# Translations

The user interface is multilingual; **German is the source language**, English comes on top. Which language a user sees is described in
`docs/users-and-login.md` (section “Language”).

## Structure

- Texts live in **Fluent catalogs** (`locales/<code>/*.ftl`, [syntax](https://projectfluent.org/fluent/guide/)), the same files for every language.
  They are embedded into the binary at build time (`rust-embed`); nothing is loaded at runtime.
- Code: `src/i18n.rs`. `Lang` is a language; `t.get("id")`, `t.get1("id", "name", value)`, `t.get2(…)` and `t.fmt("id", &[…])` return texts.
  Every page has the template field `t` (the user's language, on the login page the browser's).
- Messages from the domain logic (validation, conflicts) are `Msg` values (`Msg::new("id").with("name", value)`) and are only translated where they are shown;
  `Error::Invalid`/`Error::Conflict` carry a `Msg`. A `Msg::Text` is shown unchanged (e.g. error texts from a device).
- Error pages without a form (e.g. “Not found”) use the language of the request (`i18n::current()`, set in `web::request_language` and after login in the
  `CurrentUser` extractor).
- Numbers in German texts get a decimal comma (formatter of the German Fluent bundles).
- `sensors::format` formats values, units and threshold fields per language (decimal comma or point, “Std.”/“h”).
- Stored messages (sensor state, event log, e-mail send log) are kept as an encoded `Msg` in the database (`Msg::encode`/`decode`) and thus appear in the
  viewer's language. Older entries from before the switch stay plain German text.
- Notification mails have **one** language for all recipients, set on the page “E-mail” (`MailConfig.language`, `alerting::compose(t, …)`);
  times in mails stay UTC.
- Catalogs per area: `common` (frame, status, shared words), `users`, `devices` (groups, devices, overview), `sensors` (sensors, discovery, detail page),
  `values` (find values, known tables), `mibs`, `templates`, `credentials`, `mail`, `order`, `js` and others such as `server` (values of this server).

## Texts in JavaScript

- The scripts in `static/` get their texts from a JSON data block in the page frame
  (`<script type="application/json" id="i18n">`, generated by `Lang::js_texts()`); the CSP allows it because it is not executed.
- It contains all messages from `js.ftl` (IDs `js-…`, without the prefix in the script): `T('samples-sum')` or `window.opennetmonText(…)` from
  `static/theme.js`. Placeholders are called `%1`, `%2` (`T('samples-from-many', n)`); Fluent variables are not allowed in `js.ftl` (a test checks this).
- Date and number formats come from the catalog as well: `js-decimal` (`,`/`.`), `js-date` (`DD.MM.YYYY`/`MM/DD/YYYY`), `js-day`.
- The tests search for `T('…')` in `static/*.js`: every ID used must exist, and every `js-` message must be used.

## Rules

- Message IDs in lower case with hyphens, prefixed by area (`nav-…`, `login-…`, `users-…`, `flash-…`).
- Variables (`{ $name }`) and plurals through selectors:

  ```ftl
  login-wait-minutes =
      { $minutes ->
          [one] { $minutes } minute
         *[other] { $minutes } minutes
      }
  ```

- askama escapes placeholder values when inserting them into HTML; catalogs contain **no HTML**.
- The tests in `src/i18n.rs` check that all catalogs are free of errors, that every language has the same files, messages and variables as German, that every
  ID used in code or templates exists and that every message is used.

## A new language

1. Add the language to `Lang` in `src/i18n.rs` (`ALL`, `code`, `native_name`).
2. Copy `locales/de/` to `locales/<code>/` and translate it (or start from `locales/en/`); plural forms follow the rules of the language (CLDR, e.g. `one`,
   `few`, `many`, `other`).
3. `cargo test` – the catalog tests show missing or surplus messages.

Not translated are stored names (devices, groups, sensors, templates), values from devices and the project documentation in `docs/` (English only).
